description: How WatchConnectivityModule gets registered with expo-modules-autolinking using a local workspace package instead of runtime patching

## Rule
Register bare Swift modules (not npm packages) with expo-modules-autolinking by creating a local pnpm workspace package with `expo-module.config.json` + `.podspec`. Never try to patch `ExpoModulesProvider.swift` after pod install.

## Why
`ExpoModulesProvider.swift` is generated by `use_expo_modules!` during `pod install`. There is NO reliable hook between `pod install` and `xcodebuild` to patch it:
- `withDangerousMod` (Podfile patch) runs before Expo's Podfile base mod overwrites the file
- Xcode Run Script build phases embedded in pbxproj have string-escaping constraints that caused silent failures (embedded Python heredoc, awk print with double-quotes)
- Three successive builds (1.0.45–1.0.47) all failed via the patching approach

The correct fix: make autolinking itself generate the provider with the module included.

## How to apply
1. Create `packages/<module-name>/` with:
   - `package.json` (private: true, name, version)
   - `index.js` (stub — JS not needed)
   - `expo-module.config.json` with `"ios": { "modules": ["SwiftClassName"], "swiftModuleName": "", "podspecPath": "<module-name>.podspec" }`
   - `<module-name>.podspec` (valid podspec, no `source_files` — the Swift file is already in the main target)
2. Add `packages/*` to `pnpm-workspace.yaml`
3. Add `"<module-name>": "workspace:*"` to the mobile app's `package.json`
4. Run `pnpm install`

### `podspecPath` is REQUIRED
`findPodspecFiles` uses `listFilesInDirectories`, which only searches **subdirectories** of the package root — it never looks at files in the root itself. Without `podspecPath`, `resolveModuleAsync` returns `null` (no podspec found → nothing registered). `podspecPath` bypasses `listFilesInDirectories` entirely, returning the config-provided path directly. Confirmed: builds 1.0.47–1.0.48 silently failed because `resolveModuleAsync` returned `null`.

### The `swiftModuleName: ""` trick
`appleSwiftModuleNames()` calls `arrayize(config.ios.swiftModuleName)`. `arrayize("")` = `[""]`.  
`getSwiftModuleNames(pods, [""])`: condition `[""] && 1` is truthy → returns `[""]`.  
In outer code: `[""].filter(Boolean)` = `[]` → no `import X` generated in ExpoModulesProvider.swift.  
This is needed because the pod has no Swift sources; importing it would fail to compile.

### Why no import is needed
Both `ExpoModulesProvider.swift` and the bare Swift module file (`WatchConnectivityModule.swift`) are compiled into the same Swift module (main app target). Swift resolves the class without any `import` statement — it's already in scope.

### Podspec requirement
expo-modules-autolinking's `resolveModuleAsync` returns `null` if no `.podspec` is found — so the package is ignored. A minimal podspec with no `source_files` satisfies this requirement without conflicting with the main target's copy of the Swift file.
